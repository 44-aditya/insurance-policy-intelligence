# Baseline PDF extraction quality report

## Experiment and decision

This experiment asks whether PyMuPDF's default page-level plain-text extraction
is sufficiently faithful to support the first Stage 1 retrieval experiment. It
does not test retrieval itself. PyMuPDF was selected as the smallest practical
baseline: it reads PDFs locally, exposes page boundaries directly, and does not
require OCR, an external API, or a document-processing framework.

**Run status:** blocked in the current build environment. The environment did
not contain PyMuPDF, and both the configured network proxy and a direct PyPI
connection prevented dependency installation. Therefore no parser output or
visual comparison is represented as completed in this report. Switching to a
different parser would undermine the requested baseline, so no silent fallback
was used. Run the documented command in an environment that can install the
declared dependency, then replace this status with measured results before using
the extracted pages for Stage 1 RAG.

## Measurements to record

`artifacts/extraction/extraction_metrics.json` is generated by the extractor and
contains the following objective measurements:

| Measurement | Result |
| --- | --- |
| PDFs processed | Pending successful PyMuPDF installation and run |
| Pages per PDF | Pending |
| Pages with no extracted text | Pending |
| Extracted characters per document | Pending |
| Extraction errors | Dependency installation blocked; PDFs not opened |

An extraction that returns non-empty text is not, by itself, evidence of faithful
extraction. Before accepting this baseline, render and compare representative
pages from **each** of the four PDFs. For each document, sample normal prose, a
definitions or numbered-clause page, and a table or structured-benefit page where
available. Record the PDF page numbers reviewed and assess:

- whether heading text is present and positioned before its section;
- whether clause numbers remain attached to the correct clause text;
- whether bullet markers and item boundaries remain distinguishable;
- whether table cells flatten in a comprehensible row/column order;
- whether recurring headers and footers interrupt sentences or sections; and
- whether multi-column or positioned content appears in a usable reading order.

## Current observations

No document-level quality observations are claimed. The four raw PDFs are
present and metadata identifies all four products, but this environment lacks a
working renderer/parser with which to make the required representation-versus-
layout comparison. Using raw PDF bytes or a second parser as a proxy would not
answer the experiment's question about PyMuPDF.

## Expected limitations and failure modes

- Plain text does not preserve font size, weight, coordinates, or table borders.
- Default reading order may interleave columns, callouts, footnotes, or table cells.
- Headers and footers are intentionally retained and may pollute later retrieval.
- Scanned/image-only pages yield no text because this experiment does not use OCR.
- Embedded character mappings can produce missing or malformed glyphs even when
  the page looks correct, so visual review remains necessary.
- A damaged/encrypted PDF or metadata mismatch is recorded in the generated
  metrics; the command exits non-zero when any error is present.

## Cost, security, and next decision

The experiment requires no paid API usage and has zero external API cost. It
processes only repository-controlled public policy documents, makes no network
calls, and creates output under `artifacts/`, not in the authoritative raw corpus.

The recommended next step is to run the extractor with PyMuPDF installed,
complete the page-level comparisons above, and commit the generated JSONL,
metrics, and measured observations. Only then should the human architect decide
whether this baseline is adequate or whether a separately measured layout-aware
experiment is justified.
